## 仓库职责

- plugin 拥有应用组、scope、应用支持登记、用户 scope 授予、应用权限声明元数据、内置与退役约束、管理 UI/API、业务存储和 Kestra 实际策略。
- overlay 只提供公开宿主机制和必要激活点，保留标准 OIDC 账号、client、协议端点、签名与校验。应用组身份和 scope 签发所需的数据通过版本化只读投影取得，不在宿主重复实现组业务 CRUD、组表或组初始化 CLI。
- root 选择正式宿主和插件产物，维护 Compose、CI 和真实组合验收；不得用跨仓源码或未发布产物形成构建依赖。

现有应用组候选把组目录、scope CRUD 和生命周期表放在 overlay，属于待纠正的旧模型归属沿用，不是本节的例外。OIDC 协议基础设施例外不得扩展为应用组业务存储例外。移除旧宿主业务实现时，不保留旧可写目录、旧表或旧 CLI 的兼容转发。

## 应用组和应用

“应用组”是原“应用项目”的新用户术语。它表示应用、scope 标识和应用组内用户 scope 授予关系的组织范围，避免与业务项目或开发工程混淆。

应用是接入应用组的具体系统。应用通过 OIDC 接入，是应用组成员。当前 Kestra 应用属于第一个内置应用组的普通应用成员，没有额外的身份类别。

第一个应用组是内置应用组，不允许删除。应用组列表使用卡片入口；点击卡片进入只读详情，用户主动点击编辑后才进入编辑状态。查看和修改权限分别检查。

## Scope

应用组声明 scope 标识。scope 在应用组内承担 RBAC 角色标识的作用，不包含应用组级资源和动作权限。

scope 具有三个字段：`key` 是简短英文稳定标识，`name` 是人类可读的 RBAC 角色名称，`description` 是角色用途说明。`key` 创建后不可修改或改名；应用组可以新增 scope；scope 删除为受限删除（R13）：被任何权限激活条件或 subject 授予引用时拒绝删除并在确认弹窗中列出阻塞引用，不级联清理。需求权威见 `docs/access-control-ui-requirements.md`（v2）。

## 用户、应用和权限

应用组内的用户与 scope 绑定，决定用户获授哪些 scope。scope 相当于 RBAC 模型中的角色。

应用接入应用组时，主动声明或登记支持哪些 scope，并为 scope 登记应用权限元数据。登记是应用内部实现的镜像，用于表示支持范围和在 OAuth2 授权页展示，不是应用运行时权限的事实来源；它可能与应用代码不同步。

应用权限登记至少包含独立的权限 `key` 和人类可读的权限 `name`。scope `key/name` 与应用权限 `key/name` 是两组不同字段。

```text
该应用可授权的 scope 范围 = 该应用主动声明或登记支持的 scope 集合
用户在该应用可获得的 scope 上限 = 应用可授权的 scope 范围 ∩ 应用组授予该用户的 scope
```

## OIDC

当前方案使用真正单一的 issuer 和共享的 OIDC discovery、authorization、token 等端点。应用组区分使用经过签名并验证的应用组 claim，不修改 `iss` 编码应用组，也不放宽标准 issuer 校验。

多 issuer 延期到当前完整功能由用户验收后再单独立项。本轮不得增加多 issuer 路由、发现端点、配置入口或兼容分支。应用组可以新增，新增应用组仍使用同一 issuer 和共享协议端点。

## 页面职责

- 概览：查看应用组基本信息（显示名称、组描述）和入口，不展示应用组级授权配置状态。
- scope：管理应用组声明的 scope `key`、`name`、描述和受限删除。布局同应用页签：scope 列表侧栏（key 条目）+ 详情内容区（key 只读、名称/描述编辑、删除、以及"以该 scope 为激活条件的权限"切片表——维护入口在应用页签）（2026-10-22 推广裁决）。
- 应用（2026-10-22 维护者裁决）：admin 后台管理的是 client 的**接入登记与配置**，**不存在 OAuth2 授权批准语义**——真实的应用批准发生在用户登录并授权给该应用时，是对 token 的**临时授予**，不是与应用的持久关系；持久化的用户-应用授权若将来需要，另立表与页签，当前不考虑。**约定：应用 key ≡ OAuth2 client_id**（同一值、两个语境的名称；token 的 aud claim 也用该值）；应用 key 创建后不可修改。**client secret 在应用详情显示与管理**（掩码默认、按需显示明文、重新生成入口；不可内联编辑）——宿主 `oidc_client` 表以 pbkdf2 哈希存储，实施时"显示明文"需通过重新生成时一次性下发实现（实施差异项，涉及宿主契约）。布局为应用列表侧栏 + 详情内容区（对齐宿主插件页）；「应用运行时权限」以应用自身权限为组，权限↔scope 多对多，激活条件为「应用组 key + scope key」组合且显示具体值；权限明细即实际策略 grants（参与运行时资源授权，一表一编辑入口，不设独立实际权限分节——2026-10-27 维护者最终裁决）；添加/编辑共用右侧抽屉（编辑锁定权限 key），支持最大化。
- subject（页签为专有名称，恒英文）：以 subject 为主视角——subject | 已授予 scope（tag 点击跳 scope 页签并选中）| 涉及应用 key（点击跳应用页签、选中应用，并以该 subject 持有的全部 scope 筛选运行时权限表，显示 subject 筛选 chip）（2026-10-22 维护者裁决）。

不设独立的"应用权限声明"页签（2026-10-22 维护者裁决：整体删除，此前的只读总览方案一并废弃）；权限声明的展示与维护全部在应用页签的运行时权限区完成。

命名规则（2026-10-22 维护者裁决）：OAuth2 专有名称（Issuer、Audience、scope 等）在组详情等协议语境位置**恒显英文、不随语言切换**；应用组—应用语境的概念使用应用语境命名（应用 key、应用描述），不使用协议语境叫法（客户端 ID、受众）。

不存在“身份目录”“本地权限”“应用组级 scope 配置状态”或“完整应用组恢复”这些目标概念。应用权限必须在具体应用上下文中说明。

## 2026-10-20 授权裁决

维护者已授权本轮主控裁决以下实施规则。该裁决用于实现和验收，不能把尚未发布的代码写成现有能力。

1. 英文标识使用 `application-group`（路径和配置段）、`applicationGroup`（JSON 字段）、`application_group`（数据库字段和自定义 claim 内字段）、`ApplicationGroup`（代码类型）。用户可见名称统一为“应用组”。旧 `project` 路径、字段、claim 和配置不保留兼容别名。协议标准的 issuer、audience、scope 不改名。
2. Kestra 的运行时资源授权事实来源保留在插件数据库策略，由插件管理，属于 Kestra 应用自身的实现。应用页维护的 `scope → 应用权限 key/name` 登记是另一份元数据，不能作为资源授权决策或完整 grants 的上界。插件可以分别提供“声明元数据”和“Kestra 实际权限”管理入口，但文案必须清楚区分。
3. OIDC 请求包含应用未登记支持、用户未获授或未定义的应用组 scope 时，整个请求拒绝；不静默收窄签发。`openid` 等协议 scope 独立按标准规则处理。已签发 token 若包含未知、已撤销或不再受应用支持的应用组 scope，资源请求整体拒绝；refresh 重新核对当前交集。
4. 首个内置应用组由安装时固定的内置标识识别，不根据列表顺序或可删除的 client 成员记录推断。其标识由正式安装流程创建并持久保存；内置应用组的删除和标识修改始终拒绝。第一方 UI client 标记保留为宿主登录安全机制，不作为应用组特殊身份或权限来源，不在普通应用页展示为角色。
5. scope `key` 使用小写 ASCII 字母开头，后续仅允许小写字母、数字和连字符，长度 1–64；在应用组内唯一且创建后不可修改。`name` 和 `description` 可以独立修改；`name` 必填、同组内唯一，按 Unicode 原值精确比较，不自动翻译或折叠大小写。`description` 可空，不参与授权。应用权限元数据的 `key` 在具体应用内唯一且稳定；其 `name` 必填、可修改。多语言界面只翻译固定 UI 文案，不自动翻译管理员输入的名称。
6. 删除 scope 时，服务端必须在同一持久化操作中确认该组所有应用均未登记使用。用户授予如果仍引用该 scope，删除操作拒绝并要求先撤销授予；这避免静默改变用户关系。撤销应用支持或用户授予必须使旧 token、refresh 和 UI/MCP 会话在现有撤权时限内失效。
7. 应用组列表仅展示卡片和基本信息，不展示配置状态或“两侧分别保存”。详情初始只读；有修改权限者点击“编辑”后才能修改。scope 页称“scope”和“角色名称”，应用页称“应用权限声明”，Kestra 资源策略页称“Kestra 实际权限”，用户页称“scope 授予”。旧 reconciliation、local binding、identity directory 等用户入口及翻译键删除，不换名保留旧流程。并发冲突通过当前对象版本、重新读取和精确重试提示处理。

## 2026-10-21 删除安全补充裁决

组 ID 在同一安装内按生命周期唯一。删除非内置组时，必须在同一目录写锁及数据库事务中保存退役 ID，再删除组记录；内置组及被拒绝的删除不得写入退役记录。创建组必须同时检查现存和退役 ID，不得复用退役 ID。此约束防止新组的初始版本重新匹配旧组凭据，不提供完整应用组恢复或旧 ID 复用流程。

普通组删除须满足：当前可信身份具有管理权限、对象修订精确匹配，且没有 scope、应用成员或用户授予引用。第一个内置组始终不可删除。退役记录是插件业务持久化约束，不是用户授权、角色或应用权限声明；不能因此授予任何资源权限。上述是本轮已授权主控裁决，数据库、并发与真实组合仍必须按正式产物验收。

## 验收

- 应用组卡片、只读详情和显式编辑通过真实浏览器。
- scope key/name/description 和受限删除通过 UI、REST 和存储检查。
- 应用支持 scope 登记与应用权限元数据 CRUD 通过真实应用上下文检查。
- 用户 scope 授予与应用支持范围交集通过真实登录、REST、MCP 检查。
- 同 scope 授权完整，禁止跨 scope 拼接；拒绝操作核对数据库、队列和存储无副作用。
- 单一 issuer、签名应用组 claim、issuer/audience/application-group/client 边界和撤权通过安全验收。
