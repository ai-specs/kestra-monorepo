# 应用组 UI 术语优化

“应用组”原称“应用项目”。改名是为了明确它是应用、scope 标识及用户 scope 授予关系的组织范围，避免与组内的具体应用、业务项目或开发工程混淆。下文旧页面事实、历史原话与代码标识保留原名称以便定位；它们不是目标术语。

状态：术语、应用与应用组关系、应用支持 scope 范围、应用组卡片与先查看后编辑，以及
单一 issuer 与应用组 claim 方案已由维护者确认。具体替换文案和内置应用组识别方式仍按
相应章节裁决；本文新增要求的实现与真实浏览器复验未开始。

实施规范：当前实施规范与验收规则见根仓 `docs/application-group-target-model.md`。本文
保留裁决原文、事实清单与待裁决建议，作为目标模型的追溯依据；目标模型转写与本文 §2
裁决原文不一致时，以本文 §2 为准，并回改目标模型。

本文只记录应用组管理页面（`/ui/main/extensions/rbac/**`）的用户可见术语、概念定位
与说明文案，并记录维护者后续澄清的目标模型。新增裁决可能与现有模型不一致，不能
一概当作术语替换。实现前须同步所属仓库的需求与契约；旧实现和既有验收不能证明
已经满足这些新增裁决。

本文分三层记录，不得混用：

- **已裁决**：维护者已明确的结论，实施必须遵守。
- **事实清单**：当前代码与页面的实际状态，用于界定影响面与裁决落地的前提。
- **实施方建议**：尚未经维护者确认的方案，不得当作结论写入 UI。

## 1. 问题记录

### 1.1 第一项问题（2026-10-20，维护者提出）

页面路由：

```text
/ui/main/extensions/rbac/projects
```

该页面当前是**应用组列表页**，顶部显示提示（翻译键 `independentSaves`）：

```text
zh_CN：身份目录与本地权限分别保存，任何一侧保存都不会自动同步另一侧。
en   ：Identity directory and local permissions are saved separately. Neither save synchronizes the other.
```

维护者指出：

1. "身份目录"叫法不合适，太拗口。这个概念就是 `scope`，直接使用 `scope` 这个专用
   名词即可。
2. "本地权限"叫法不恰当。"本地"只能相对于应用组里的某个具体应用而言。

并且，应用组列表页当前只是一个应用组列表，尚未引入 scope、应用、授权内容等任何其他概念；
在这个页面提示"身份目录""本地权限"都不合理。

### 1.2 第二项问题：根本性定位（2026-10-20，维护者提出）

维护者原话：

> 这里要纠正一个根本性的定位问题，当前应用也是第一个"项目 ID"里的一个应用，当前应用
> 使用 OIDC 协议接入，本身就是项目里的一员，没有什么特别的；同时也得出第一个项目是
> 内置项目，不允许删除。所以不存在所谓的"本地"，而是"相对应用"来说权限。

三个结论：

1. **当前应用（Kestra 自身）是第一个应用组中的一个应用成员**，通过 OIDC 接入，与应用组中
   其他获准 client 地位相同，没有特殊身份。
2. **第一个应用组是内置应用组，不允许删除。**
3. **"本地"这个概念不存在。** 插件保存的授权内容是"某个应用对 scope 的权限"，即权限
   相对于应用而言。

### 1.3 早期解释及其适用边界

实施方对"两侧分别保存"的解释——scope 的定义与授予（谁能取得哪个 scope）和应用对
scope 的权限（该 scope 在该应用中能对哪些资源做什么）是两套独立配置、保存一侧不会替
管理员完成另一侧、完整授权需要两侧同时成立——维护者未提出异议。

以上仅记录早期讨论，不能把维护者未提出异议当成对所有实现机制的确认。
后续 §2.9 明确撤回“应用组 scope 定义变化触发完整应用组恢复”的解释与流程依据。

### 1.4 第三项问题：应用支持 scope 与用户获授 scope 必须分开

维护者明确：应用支持哪些 scope，指哪些 scope 已绑定该应用的权限；用户获得哪些
scope，由应用组内的用户与 scope 绑定关系决定。此时 scope 对应 RBAC 模型中的角色。

实施方此前将“是否获准请求哪些 scope”描述为每个应用 client 自己的授权状态，混淆了
应用支持范围与用户角色授予；该描述撤回。此前将完整 grants 说成整个应用组共享一份、
与具体应用无关，也不符合本次澄清。

## 2. 已裁决（维护者确认）

### 2.6 应用组 scope、用户授予与应用权限的关系

- 应用组声明 scope 标识；它作为应用组内用户角色的标识，不包含应用组级资源和动作定义。
- 应用组内的用户与 scope 绑定，决定该用户被授予哪些 scope。
- 应用为 scope 绑定自己的权限，决定该应用支持哪些 scope，以及各 scope 在该应用
  中允许访问的资源和动作。
- 应用支持某个 scope，不代表用户已获授该 scope；用户获授某个 scope，也不自动
  为所有应用创建该 scope 的权限配置。
- 用户在某个应用中的实际权限，必须同时满足应用组中的用户 scope 授予与该应用对
  同一 scope 的完整权限配置；issuer、audience、有效期等协议校验仍须成立。

应用主动登记支持的 scope 集合，构成该应用申请 OIDC 授权时可授权的应用组 scope 范围。
登记的 scope 与应用权限对应关系是应用内部实现的元数据镜像，可能与代码不同步；它不是
应用运行时权限配置来源。具体关系见 §2.12。

对应用组 scope 而言，授权结果必须同时受以下两个集合约束：

```text
该应用可授权的 scope 范围 = 该应用主动声明或登记支持的 scope 集合
用户在该应用可获得的 scope 上限 = 应用可授权的 scope 范围 ∩ 应用组授予该用户的 scope
```

具体授权请求中未请求的 scope 不得自动签发；请求包含范围外 scope 时采用拒绝还是
收窄策略，尚待协议行为裁决。`openid` 等协议 scope 与这里的应用组角色 scope 分开处理，
不能要求它们绑定业务权限才能完成 OIDC 登录。上述范围规则不替代签名、issuer、
audience、有效期和实际资源权限校验。

应用支持范围不得再描述为应用替用户获得哪些 scope 的独立角色授予。

### 2.7 不存在“应用组级 scope 配置状态”

应用在接入应用组时，声明或登记自己支持哪些 scope，即哪些 scope 已绑定该应用的
权限。这个支持范围属于具体应用与其接入应用组的关系，不属于应用组整体的配置状态。

应用组定义 scope、用户在应用组中获授 scope，不产生“应用组级 scope 配置状态”。应用组内有
多个应用时，不得把各应用支持范围合并成应用组的“已配置”“部分配置”或“待配置”状态。
实施方此前提出的应用组级状态及各应用汇总状态方案撤回。

应用组列表中的“本地绑定”列应删除，不得仅更名为“授权配置”“Scope 配置”或“应用权限”
后保留原来的应用组级状态语义。具体应用的页面或应用接入记录应展示“支持的 scope 范围”，
并明确其所属应用和应用组；scope 的应用权限明细在该应用上下文中展示。

当前实现中的 client scope 限制、共享 scope 意图上界、第一方标记与上述关系是否一致，
必须继续调查并记录差异；不得仅靠更名就宣称代码已经符合。本项是模型澄清，若与既有
`application-projects.md` 的说明冲突，后续方案必须显式协调，不能假称只是文案修改。

### 2.1 不再使用"身份目录"，统一使用 `scope`

用户可见文案中不再出现"身份目录""共享身份目录"及其英文 "identity directory"
"shared identity directory"。该概念统一称为 `scope`。

本裁决是术语级裁决，适用于所有页面，不限于应用组列表页。

### 2.2 权限相对于应用而言，"本地"整体废止

用户可见文案中**不再出现"本地"**——包括"本地权限""本地绑定""本地 grants"
"本地 scope 绑定"及其英文 "local permissions / local binding / local grants"。
这是整体废止，不是"页面明确应用时才可用"的条件性保留。

插件保存的授权内容是**某个应用在所属应用组的 scope 下可以访问哪些资源、执行哪些动作**。
在 Kestra 自己的管理页面中，这个应用就是**当前应用**（用户正在登录的这个 Kestra），
参照对象始终确定，不需要用"本地"来暗示。

替换用什么词见 §4.2（待裁决）。

### 2.3 应用组列表页不提前解释尚未出现的概念

`/ui/main/extensions/rbac/projects` 当前只展示应用组。该页面不应出现"身份目录"
"本地权限"，也不应提前解释该页面尚未引入的概念（scope 授予、client 成员、subject
分配、grant 保存流程等）。

"两侧分别保存"的提示应移到**概念已经出现**的页面（见 §4.3 建议），而不是放在列表页。

### 2.4 当前应用是内置应用组中的普通成员

当前应用通过 OIDC 接入，是第一个（内置）应用组中的一个应用成员。当前应用没有独立于
应用组模型之外的特殊身份，不应在 UI 文案中被描述成"身份目录"或任何额外的身份系统。
它与同一应用组中的其他获准 client 一样，按该应用组的 scope、audience 和成员授予规则工作。

应用组列表页用"应用组 ID""应用组"说明当前对象，不引入额外概念。

> 注意：这是定位与用词层面的裁决。当前实现中第一方 UI client 带有 `firstPartyUi`
> 标记并有专属约束（见 §3.4）。该标记是否保留、如何向用户呈现，不属于本文已裁决范围，
> 见 §4.6。

### 2.5 第一个应用组是内置应用组，不允许删除

第一个应用组必须始终存在，不允许删除。应用组列表与应用组详情可以展示其内置状态，但不得把
它显示成可删除的普通应用组，也不得让任何删除操作产生误导性的成功提示。

> 当前实现没有"删除项目"的 API 或按钮（见 §3.4），本裁决目前靠"能力不存在"成立。
> 若将来增加项目删除能力，必须排除内置项目。内置项目如何识别与呈现见 §4.5。

### 2.8 应用组采用卡片展示，先查看再编辑

应用组数量少，当前只有一个。应用组集合入口采用卡片展示，替代现有表格。
点击卡片进入只读详情，不直接编辑。详情页提供明确的“编辑”按钮，有修改权限的用户
主动点击后才进入编辑状态。查看与修改权限分别校验；取消不得保存未提交变更。

应用组入口不需要“操作”列，也不在卡片上默认显示“编辑”作为主要入口。卡片不显示
应用组级授权配置状态。卡片字段、内置标识、键盘操作、明暗主题和窄屏布局须实际验证。
此前章节中的“应用组列表页”指应用组集合入口，不要求保留表格布局。

### 2.9 应用组 scope 标识不可修改，权限含义归应用

应用组声明的 scope 以 key 作为标识，并提供 name 和描述作为角色展示信息，见 §2.11。
已有 key 只读，不允许修改或改名；应用组可以添加
新标识。删除某个 scope 的前提是应用组中的所有应用均已登记不使用该 scope，只要还有
应用登记使用就不得删除。未登记使用与缺少应用状态不能混为一谈。

scope 的具体权限含义只在应用接入应用组、登记承认该 scope 并绑定应用权限后成立。
应用组 scope 不保存一份供所有应用继承或收窄的资源、动作或命名空间定义；不同应用
各自解释同一角色标识在自身资源中的权限，不能从 scope 名称推导权限。

因此，不存在需要管理员处理的“应用组 scope 定义已变化”情形。实施方此前以此解释
“审核完整应用组恢复”，以及提出仅更名为“检查应用权限”的处理方式，均撤回。
不得要求用户因应用组添加 scope、用户授予变化或其他应用登记变化，重新审核当前应用
全部权限并手工填写目录修订。用户撤权及应用自身权限变更仍须及时生效，不能因取消
该恢复流程而放松身份校验或继续使用已撤销的权限。

当前 shared intent 上界、全应用组目录修订失配、`reconciliation` 页面及强制恢复门属于
待核对和调整的实现差异，不是目标模型中的必然要求。并发写入保护可以保留为内部
机制，但不得把内部版本处理直接转嫁成用户的“完整应用组恢复”。

scope 删除时现存用户授予、token 与应用登记如何一致处理，须单独明确；本次不推断
自动解绑、级联删除、重命名或旧新 scope 自动替换。

### 2.10 名称统一覆盖当前实现

当前实现从未通过维护者验收，不以旧名称的兼容性为前提。应用组命名必须覆盖用户界面、
文档、API 路径、请求与响应字段、数据库表及字段、配置项，以及签名 token 中用于表达
应用组的 claim 名称和相关代码标识。不能只更改 UI 后继续将旧 project 命名作为正式契约。

协议本身的标准名称（例如 issuer、audience、scope）保持标准语义；只修改本系统用于
表达应用组的自定义名称。历史原话、Git 历史及明确标注的旧实现事实不机械改写。

具体英文标识及路径清单须调查当前实现后在所属仓冻结，并同步签发端、消费端、存储、
管理 UI 和测试。不为旧 project 路径、字段或 claim 额外增加双读、别名或兼容分支；
开发测试数据可以重新初始化，不把旧开发数据迁移作为本轮交付门。

本条是当前实施范围，不是延期事项。必须先发布必要宿主契约，再由插件消费正式产物，
最后执行新名称对应的 UI、REST、MCP 与安全组合验收；本文更新不等于代码已经改名。

### 2.11 scope 的 key、角色名称与描述

scope 包含以下三个不同字段：

| 字段 | 用途 | 约束 |
|---|---|---|
| key | 协议和绑定关系使用的标识 | 简短英文 key，在所属应用组内唯一；创建后不可修改或改名 |
| name | 承载 RBAC 的角色名称，供用户识别 | 独立字段，不得用 key 或描述代替 |
| description | 解释角色用途 | 补充说明，不作为协议标识或权限依据 |

token 中的项目角色 scope 值以及用户授予、应用权限绑定均引用 key，不以 name 或描述
推导权限。用户界面应能同时识别角色名称和 key，例如“订单查看者（orders-read）”；
该例仅说明字段区别，不冻结具体 key 语法。

“不可改名”针对稳定 key，不得通过修改 name 或描述暗中替换 key。name、description
是否允许独立修改，英文 key 的字符集、大小写与最大长度，以及 name 的重复和多语言
规则，尚待裁决；本条不擅自开放这些修改，也不把新增 name 等同于可修改 scope 标识。

### 2.12 应用页管理主动声明的 scope 与应用权限元数据

应用内部代码实现 scope 与实际权限的关系。应用页管理的是该关系的镜像，即应用主动
声明的授权元数据，用于登记应用支持哪些 scope，并在 OAuth2 授权页面说明其权限含义。
这个副本可能与应用代码不同步；应用运行时不依赖它执行资源授权。

应用页提供对应关系的增加、查看、修改和删除，但这些操作只改变登记元数据，不自动
修改应用代码、应用运行时权限规则、应用组 scope key 或用户 scope 授予。登记变化会
影响授权服务认定的应用支持 scope 范围；这与改变应用内部执行逻辑必须明确区分。

每项声明的应用权限至少具有以下独立字段：

| 字段 | 含义 |
|---|---|
| 权限 key | 应用内部权限的机器标识，用于对应登记和应用实现 |
| 权限 name | 人类可读的应用权限名称，用于授权页和管理页面展示 |

应用权限 key/name 与应用组 scope key/name 是两组不同字段，不能混用。元数据描述
某个 scope 在某个应用中对应哪些权限；OAuth2 授权页须显示可读名称，不能只展示机器
key，也不能把声明副本呈现为对应用实际行为已经完成验证的保证。

不要求每个应用采用 Kestra 的资源、动作或命名空间模型，也不要求应用运行时读取该
元数据。登记、更新及可能不同步的呈现方式须在实施时明确，不引入强制同步、全组修订
失配或“完整应用组恢复”流程。此前要求登记副本与代码强一致的表述撤回。

应用组 scope 删除前检查的仍是各应用登记的使用情况，不推断未登记的代码实现。
删除登记不等于已从应用代码删除对应权限，也不得自动给用户增加或撤销 scope。

## 4. 实施方建议（待维护者裁决）

以下为实施方拟定的方向，**未经确认，不得直接写入 UI**。每条经维护者确认后移入 §2。

### 4.1 "身份目录"侧的具体表达

- 泛指该侧对象时：`scope`。
- 指"谁可以取得哪个 scope"时：`scope 授予`（用户）、`scope 成员`或`获准的应用`
  （client）。
- `identityDirectory`（tab/区块标题）→ 建议 "Scope" / "scope"。
- `saveIdentity` → 建议 "保存 scope" / "Save scopes"。
- `directoryStale` / `reauthenticationRequired` 中的"身份目录已变化"→ 建议
  按真实事件分别说明“用户的 scope 授予已变化”或“会话已失效”，不得使用
  “应用组 scope 定义已变化”或继续引导完整应用组恢复。

### 4.2 "本地"侧的具体表达：以"应用权限"命名

按 §2.2，授权内容是"应用对 scope 的权限"。建议统一用 **"应用权限"**（英文
"application permissions" 或 "scope grants"）系表达，参照对象为当前应用：

- `localPolicy` → "应用权限" / "Application permissions"。
- `completeGrants` → "完整 grants"（去掉"本地"）。
- `localStatus`：应用组列表列删除，不作应用组级状态的术语替换；应用接入记录展示
  “支持的 scope 范围”，不使用一个布尔或汇总状态代替实际 scope 集合。
- `saveLocal` → "保存应用权限"；`localSaved` → "应用权限已保存；scope 授予未同步修改。"
- `deleteLocal` → "删除该 scope 的应用权限"；`newLocalBinding` / `addLocalScope` →
  "为 scope 配置应用权限"；`configureLocalFirst` 的候选文案必须明确具体应用，
  不使用“先为应用组配置应用权限”的应用组级描述。
- `reviewedBinding` / `reconciliationSaved` / `stateDisclaimer` 中的"本地绑定"→
  "应用权限配置"。

在 scope 详情页，授权内容直接按实际字段说明：命名空间范围、资源类型、动作、是否含
子命名空间、资源 ID 限制、管理目标（若该页确有管理 scope）。页面应显示当前应用的
名称或 client ID，让"相对哪个应用"一目了然。

### 4.3 "两侧分别保存"提示的去处与文案

- 应用组列表页：**删除** `independentSaves` 横幅。如需引导，用只描述本页行为的一句，
  例如"选择应用组后查看并维护该应用组的 scope。"——以页面实际可执行操作为准，不提示
  本页不存在的操作。
- 应用组详情 / scope 详情页（两侧对象都已出现）：保留"分别保存、互不同步"的提示，
  改用新术语，例如"scope 的授予与当前应用的权限分别保存，保存任一侧不会自动同步
  另一侧。"

### 4.4 概念引入顺序

1. 应用组列表：应用组（含内置应用组标识）；进入应用组的入口。
2. 应用组详情：应用组 ID、issuer、audience、启用状态、修订；本应用组中的应用成员（含当前应用）。
3. 应用组的 scope 列表：scope 名称、说明、启用状态；不展示应用组级应用权限配置状态。
   应用接入记录展示该应用声明或登记的支持 scope 范围。
4. scope 详情：同一 scope 内的命名空间、资源、动作、子命名空间、资源 ID 限制。
5. 成员 / 用户：scope 授予、应用（client）批准、subject 分配，标明其属于哪一侧保存。

页面不得把一个 scope 拆成"命名空间选择器"和"动作角色"两个独立来源，也不得用术语
暗示不同 scope 可以拼接出新权限。

### 4.5 内置应用组的识别与呈现

- **识别规则（建议）**：内置应用组 = 第一方 UI client（当前应用）所属的那个应用组。依据
  §3.4 "同一第一方 UI client 不得同时属于多个应用组"，该应用组唯一确定，无需新增数据库
  标记即可推导；若维护者希望显式标记，则在目录应用组记录上增加内置标志（涉及宿主契约）。
- **呈现（建议）**：应用组列表与详情显示"内置"标识；当前无删除动作，不新增；若将来
  增加应用组删除，内置应用组不显示删除动作并给出一句说明（"内置应用组不可删除"），而不是
  显示后再报错。
- **边界**：内置应用组的 scope、应用成员、授予仍可正常维护；"不可删除"只针对应用组本身。

### 4.6 第一方标记的呈现与归属（可能超出术语范围）

`firstPartyUi` 标记有实际协议功能（应用组选择器、audience 校验、单应用组归属），不能只靠
改文案消除。两个方向供裁决：

- **A. 保留标记，仅调整呈现**：用户可见文案把当前应用展示为普通成员（名称 + client
  ID），不显示"第一方""身份目录"字样；选择器等协议行为不变。本文范围内可完成。
- **B. 去除标记，泛化为普通成员**：需要重新定义应用组选择器与 audience 校验的依据，
  涉及宿主公开契约变更，超出本文（术语）范围，须另立需求并先改宿主。

实施方建议 A，待维护者裁决。

## 5. 术语优化不改变的授权语义

- 应用组中的 scope 只是标识；应用为它绑定权限时，必须保持完整的资源范围与动作条件。
- scope 授予不等于该 scope 在当前应用已配置权限；两侧都成立才允许。
- 未知、停用、空 grant 或无效 scope 失败关闭；已知但未配置应用权限的 scope 混入
  token 时整体拒绝。
- 不同 scope 不在运行时拼接命名空间、资源 ID 或动作。
- UI、REST、MCP 使用同一 scope 解释。

## 7. issuer 与 OIDC 端点的架构裁决

### 7.1 当前方案（维护者已确认）

保持真正单一的 issuer 和共享的 OIDC 发现、授权、token 等端点，使用经过签名并验证
的应用组 claim 区分应用组。不得修改 `iss` 来编码应用组，也不得放宽标准 issuer 校验。

- 各应用组使用相同的可信 issuer；发现元数据与 token 的 `iss` 保持精确一致。
- 应用组区分来自签名 token 中经验证的应用组 claim，不信任请求参数或未验证 token 内容。
- 签发和消费时均核对应用组、应用归属、audience 和 scope 的一致性。
- 应用支持的 scope 范围、应用组内用户的 scope 授予，以及具体应用权限仍分别检查。
- 应用组列表不将 issuer 呈现为每个应用组各自拥有或可独立配置的属性；若展示，须明确其
  为服务共享配置。具体 UI 是否展示仍按页面用途决定。

此方案优先复用上游标准 OIDC 机制，控制定制面和升级成本。应用组 claim 的具体字段、
验证和传播链必须先核对已发布契约；已有机制能满足时直接复用，不另造平行机制。

### 7.2 历史方案与延期范围

曾讨论每应用组独立 issuer，以及共享端点但在 `iss` 中区分应用组。后者从协议上仍是多个
逻辑 issuer，不能称为单一 issuer；标准 client 的发现与 issuer 精确匹配要求会增加
兼容与维护成本。这两个方案均不是本轮实现方向。

只有当前完整功能经过用户验收后，才考虑多应用组、多 issuer 的后续需求。当前允许多个
应用组共享单一 issuer；延期的是多 issuer 能力，不是现有应用组模型或应用组隔离检查。
本轮不得为尚未接收的多 issuer 需求增加路由、发现端点、配置入口或兼容分支。

本节是目标裁决，不等于实现已符合。调查发现与当前公开契约不一致时，须同步所属仓库
需求和宿主能力文档，再按独立构建与发布规则实施。
