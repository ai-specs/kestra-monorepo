# AMIS Apps 扩展需求

> 状态：需求已定稿，待实施。本文件是 `kestra-plugin-amis-apps` 的需求基线，
> 不表示对应功能已经实现、通过 CI 或发布。

## 1. 目标与来源

在当前部署项目中增加独立扩展功能集 `kestra-plugin-amis-apps`。一个独立 Flow
承载一个 AMIS 应用：页面声明、页面所需 API 和执行逻辑均归属于该 Flow。
页面使用 AMIS JSON schema 描述。新增或修改应用不需要为该应用编译和发布前端包；
扩展自身的固定前端运行时仍按独立仓规则构建和发布。

目标参照为 `~/dsh-monorepo/app-kestra`。它只用于理解用户目标，不是实现参照。
不得沿用其直接修改上游源码、构建依赖或历史约束来替代当前扩展架构。

本需求只支持当前单 tenant 部署，不设计 tenant 选择、跨 tenant 或跨实例组合。
需要不同组合时部署多个实例，这不属于本需求的实施范围。

## 2. Flow、页面与 API

- Flow 是应用声明的唯一事实来源。页面和页面所需 API 由同一个 Flow 承载，
  不增加独立应用实体、独立应用事实表或独立路由事实表。
- HTTP 入口按 Flow 的声明提供 AMIS 页面和触发对应 Flow 的 API。
- route 只是把 URL 解析到 Flow 及其声明的机制，不是另一个配置或业务事实来源。
  修改、禁用或删除 Flow 及其声明后，入口行为必须与当前 Flow 状态一致。
- 页面 schema 只允许当前 namespace 或父级 namespace 的 `nsfile:///` 文件。
  不允许引用兄弟或无关 namespace，不允许通过路径穿越扩大解析范围。
- API 必须认证，不支持匿名。执行模式默认 `ASYNC`，`SYNC` 必须显式声明。
  不以 SSE 作为 API 契约。
- 页面访问、API 调用和执行结果必须关联到同一个承载 Flow，不能用一个 Flow
  的授权访问或触发另一个 Flow。

## 3. URL 与原生路由优先

统一应用 URL 前缀为：

```text
/{namespace}/{flow_id}/...
```

namespace 和 Flow ID 来自实际承载 Flow，不引入独立 appName 替代 Flow ID。
本需求不固定前缀之后的字段名称、页面/API 子路径或 Java 类型名称。

当 namespace 对应路径与 Kestra 内置 URL 冲突时，以上游 URL 为准。
扩展不得覆盖、抢占原生路由，也不得在原生路由返回错误时将它当作 AMIS 请求处理。
此规则同时适用于原生认证、API、UI、静态资源和健康检查路径。

URL 的编码和路径安全检查必须保留，不能通过编码或路径穿越绕过原生路由优先规则。

## 4. 统一权限配置

`kestra-plugin-amis-apps` 与 `kestra-plugin-rbac` 均是 Kestra UI 应用的扩展。
新增扩展仓不等于新增身份目录中的应用。

- 不因本功能新增 OAuth client、应用成员、应用组、scope 或管理 tab。
- 不在“概览、scope、应用组”等管理导航中增加“应用”入口。
- 使用既有 `kestra-ui` 应用的“应用运行时权限”维护入口能力明细，并关联已有 scope。
- 已有等价入口能力明细时直接复用，不重复追加；缺少时才增加一条。
- 不要求每个页面、API 或 schema 文件各登记一条权限。
- 入口能力的范围表达和前缀解析规则与既有 Flow 权限明细一致，不另造范围语法。
  例如 `company.*` 不匹配 `company2`；精确范围和补集语义保持一致。
- 权限明细名称或 key 本身不是授权结果。不得只因 URL 前缀匹配就放行业务。

入口能力只决定“是否允许按 AMIS 约定进入 URL 解析流程”。它不证明 namespace、
Flow 或声明路由存在，也不授予 Flow 执行权限。

## 5. 职责与请求顺序

### 5.1 职责

| 项目 | 职责 |
|---|---|
| `kestra-overlay` | 提供可被未来扩展复用的通用扩展入口能力门、原生路由优先、可信身份传递和评估调用机制；仅在现有公开机制不足时增加最小通用契约 |
| `kestra-plugin-rbac` | 统一权限维护、当前身份与 scope 的支持/授予及运行时策略评估、撤权，以及既有 Flow 执行授权 |
| `kestra-plugin-amis-apps` | 登记入口能力及范围规则，在通用机制下判断是否进入自身解析；放行后解析 URL、查找 Flow 和声明、请求 Flow 执行授权，最后提供页面/API |
| `kestra-monorepo` | 选择正式产物、配置 Compose、协调发布顺序并执行真实组合验收，不实现 AMIS 业务 |

AMIS 插件通过公开机制消费 RBAC，不读取其私有表，不复制策略或另建许可名单。
overlay 不承载 AMIS schema、页面/API 声明或应用业务。

### 5.2 严格请求顺序

| 顺序 | 行为 | 负责项目 |
|---|---|---|
| 0 | 保留原生路由优先和生产认证；原生冲突请求不进入 AMIS | overlay |
| 1 | 按当前可信身份及 scope 判断是否具有进入 AMIS URL 解析的入口能力；此时不查询 namespace、Flow、schema 或 Flow 执行权限 | overlay 提供通用门；RBAC 提供统一权限评估；AMIS 提供并判断自身入口能力及范围 |
| 2 | 第一门允许后，按 namespace、Flow ID 解析并查找对应 Flow 和声明路由；不存在时正常返回 404 | AMIS Apps |
| 3 | 找到目标后，验证该具体 Flow 的执行权限；拒绝时停止 | AMIS 通过公开机制调用 RBAC 的既有 Flow 授权 |
| 4 | 两道门均允许后，读取声明 schema、提供页面或触发 API 执行 | AMIS Apps；实际执行使用现有宿主执行链 |
| 5 | 后续访问继续接受当前权限、撤权和适用的执行输出检查，不能沿用过期入口许可 | overlay、RBAC、AMIS 按各自职责共同完成 |

第一道门拒绝时不得查找目标，也不能通过不同响应透露 Flow 是否存在。
只拥有入口能力时，目标不存在返回 404；目标存在仍须通过 Flow 执行权限。
只拥有 Flow 执行权限时，不得绕过第一道入口能力门。

通过两道门后，读取当前或父级 namespace 的 schema 不再叠加额外文件级授权。
该规则不删除 RBAC 已有资源类型，不跳过现有执行链、输入/输出校验或执行结果权限。
页面访问许可也不授予修改 schema 或 Flow 的权限。

## 6. 安全与兼容

- 不支持匿名入口。浏览器使用生产登录流程；直接访问应用 URL 后，认证成功应返回
  原目标。cookie 写请求保留 CSRF，不能因使用简化 URL 而绕过。
- scope 授予、入口能力或 Flow 权限撤销后，后续请求必须遵守既有撤权与 refresh 机制。
  AMIS 不保存独立授权副本。
- 执行查询必须验证执行属于承载 Flow，不能通过任意执行 ID 访问其他 Flow 的结果。
- 必需组件缺失、授权依赖异常或资源计划无法确定时失败关闭。
- 拒绝请求不能创建 execution，不能写队列、存储或留下延迟业务副作用。
- 共同使用的 overlay 必须兼容模式 A 和模式 B。关闭 RBAC 时按宿主既有关闭语义
  工作，不伪造 scope，不要求授权插件存在；认证、URL 安全和原生路由优先保持有效。
- 新扩展停用或缺席时，不影响宿主原生路由和其他扩展。

## 7. 项目与文档边界

AMIS Apps 的业务声明、页面运行时、API 处理、schema 解析及自身测试归新扩展仓。
宿主只提供公共机制；根仓只维护组合与集成要求，不把业务代码放入根仓。

新扩展业务 README 与公开契约维护具体字段、类型和命令。本需求不指定未共同确认的
触发器类名、响应封装、默认同步超时、目录页、可视化设计器或机器调用方案。
这些内容不得从参照代码自动推导为本期需求。

业务文档建立后，本文件保留跨仓目标、职责、顺序和组合验收要求，避免多处重复维护。

## 8. 验收要求

独立仓使用已发布公开契约和正式产物构建，不依赖相邻源码或未发布 jar。
宿主验证通用机制，RBAC 验证统一策略兼容，AMIS 验证自身业务及真实浏览器页面，
根仓验证正式组合；任何一仓通过不能替代其他仓职责。

| 验收项 | 必须证明的结果 |
|---|---|
| Flow 承载 | 同一 Flow 声明页面及其 API，变更后无需构建应用专属前端包；无独立应用/路由事实源 |
| 路由 | namespace/Flow URL 可达；不存在目标正常404；原生 URL 冲突始终由上游处理 |
| 首门拒绝 | namespace、Flow、schema 查询和 Flow 执行授权调用均为零，无业务副作用 |
| 仅入口允许 | 不存在目标404；存在但无执行权限时拒绝，不读 schema、不创建执行 |
| 仅执行允许 | 不得绕过入口能力门 |
| 两门允许 | 真实登录后页面可用，表单/API 实际触发承载 Flow，核对执行与保存结果 |
| 权限配置 | 使用现有 `kestra-ui` 运行时权限及已有 scope；等价明细不重复追加，无新应用成员、scope 或管理 tab |
| Schema | 当前及父级 namespace 文件可用，无额外文件授权；兄弟/无关范围及穿越请求拒绝 |
| 执行模式 | 默认 ASYNC；显式 SYNC 有效；对外 API 不依赖 SSE |
| 撤权 | 分别收回入口能力、Flow 执行能力或 scope 授予，验证后续请求和 refresh 行为 |
| 拒绝副作用 | 检查 execution、队列、存储及延迟副作用，不以错误状态码单独证明拒绝正确 |
| 页面质量 | 按所属仓规则验证中文/英文、主题、窄屏、焦点、正常与错误状态；根仓不重复完整视觉矩阵 |
| 共存与关闭 | 模式A/B、与RBAC共存、新扩展停用/缺席均符合共同宿主与组合边界 |

## 9. 发布顺序

1. overlay 完成必要的公共机制，通过自身检查与 CI，发布正式镜像；无需变更的
   已发布能力只核实复用，不为形式完整制造新发布。
2. RBAC 按需要适配通用入口能力的统一维护与评估；AMIS 独立消费正式宿主契约，
   通过各自 CI 并发布正式产物。独立仓之间不读取相邻源码或触发对方构建。
3. 根仓选择兼容的正式镜像和插件，执行 Compose、真实生产登录与完整集成验收，
   核对最终提交成功 CI、实际下载报告、digest、jar hash、provenance 和资源清理。
