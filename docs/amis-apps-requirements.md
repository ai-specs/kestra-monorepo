## 1. 目标与来源

在当前部署项目中增加独立扩展功能集 `kestra-plugin-amis-apps`。一个独立 Flow
承载一个 AMIS 应用：页面声明、页面所需 API 和执行逻辑均归属于该 Flow。
页面使用 AMIS JSON schema 描述。新增或修改应用不需要为该应用编译和发布前端包；
扩展自身的固定前端运行时仍按独立仓规则构建和发布。

目标参照为 `~/dsh-monorepo/app-kestra`。它只用于理解用户目标，不是实现参照。
不得沿用其直接修改上游源码、构建依赖或历史约束来替代当前扩展架构。

本需求只支持当前单 tenant 部署，不设计 tenant 选择、跨 tenant 或跨实例组合。
需要不同组合时部署多个实例，这不属于本需求的实施范围。

### 1.1 必须保留的产品方向

必须保留“一个 Flow 承载页面与所需 API”“AMIS JSON 驱动、应用变更无需前端编译”
“复用 Kestra 执行引擎”“独立 URL”“真实页面交互与编辑器分阶段验收”的方向。
这些是需求目标，不是要求复制参照的 Java 类型、前端入口文件、任务命名或构建结构。
当前需求中已确认的新 URL、两道权限门和父级 schema 解析规则优先于参照历史选择。

### 1.2 绝对不得沿用的实现方向

下表区分“参照事实”和“当前禁止方向”。禁止项约束本项目，不表示参照项目全部
存在这些缺陷；其中匿名旁路、跨仓依赖等也是实施者不得引入的捷径。

| 参照做法、概念或容易误用的手段 | 本项目禁止方向 | 正确边界 |
|---|---|---|
| fork 内直接增加 Apps Controller、服务、前端入口和原生菜单 | 将 AMIS 业务继续写入 overlay patch、上游 core 或宿主原生 UI | 业务、独立页面及编辑器归 AMIS 插件；overlay 仅提供最小通用机制 |
| 修改 core `OutputValues` 适配应用响应 | 为响应便利修改上游通用任务或复制其内部实现 | 优先复用正式公开输出机制；必要的应用专属任务归扩展仓 |
| 与宿主源码同树构建并打包插件 | 编译新插件时读取相邻源码、旧 fork、未发布 jar，或由扩展触发宿主构建 | 正式宿主→独立扩展→部署组合，编译输入来自已发布产物 |
| 页面入口由宿主 UI 构建生成 | 每新增/修改一个应用都重编译前端或宿主镜像；直接依赖宿主 Vue/router/store 私有实例 | 固定运行时归插件，应用以 Flow 与 JSON schema 变更；使用公开 SDK/机制 |
| 旧 `appName` 别名与内存路由索引 | 恢复全局应用别名作为新事实源，建立应用/路由事实表，或每请求扫描全部 Flow | 按 namespace/Flow ID 定位；Flow storage 唯一事实源，缓存只派生且可失效 |
| 根级通配路径或旧 `/apps/{appName}` URL | 复制旧 URL 模型、抢占上游路由，或把原生路由错误回落为 AMIS | 使用本需求前缀，原生 URL 始终优先 |
| 参照早期“OIDC 登录即所有应用可达”的授权边界 | 将已登录、菜单可见、首装身份或路径匹配作为业务放行依据 | 页面/API 都先入口能力门，再解析查找，再验证具体 Flow 执行权 |
| 自定义 trigger 或 Webhook 的便利入口 | 引入匿名 Webhook 旁路；页面受控但 API、schema 或执行结果另有绕过路径 | 全部适用请求经过公共认证与两门链，保留原有执行/输出校验 |
| 独立页自有 fetcher、登录和资源装载 | 复制旧认证实现、关闭 CSRF、泄漏 token 到 schema/URL，或依赖外部 CDN 才能启动 | 复用宿主生产身份与安全机制，插件管理自己的运行时资产 |
| 编辑器可打开 namespace JSON 文件 | 把运行时父级可读许可转换成文件树管理、schema 写入或 Flow 修改权限 | 运行读取与编辑管理分离，目标 namespace/path 和写权限明确验证 |
| 旧 `<apiId>_result` 命名与响应封装 | 把旧命名或封装直接定为唯一契约，混合返回兄弟 API 输出或任意 execution 结果 | 扩展公开定义结果来源绑定并通过 P2 场景验证 |
| 参照的类名、依赖版本、CSS 注入和轮询实现 | 将历史技术约束写成新项目不可变规则，或仅凭旧报告宣布当前成功 | 功能行为借鉴，当前公开契约、锁定依赖及真实测试决定实现；API 不以 SSE 为契约 |

评审发现上述禁止方向时，必须先纠正所属项目和公开契约，再继续实施。不能以
“与参照一致”或“第一版机制移植”为由豁免，也不能用放宽权限或删减验收恢复通过。

## 2. Flow、页面与 API

- Flow 是应用声明的唯一事实来源。页面和页面所需 API 由同一个 Flow 承载，
  不增加独立应用实体、独立应用事实表或独立路由事实表。
- HTTP 入口按 Flow 的声明提供 AMIS 页面和触发对应 Flow 的 API。
- 页面入口和 API 入口都属于第一道 AMIS URL 能力门；参照项目中的 `PageTrigger`、
  `ApiTrigger` 只是描述这两类行为的参考概念，不限定 Java 类名、继承关系或唯一实现。
- 第一门必须同时覆盖 PageTrigger 对应的页面 URL 和 ApiTrigger 对应的 API URL；不能
  只保护页面而让 API 直接进入 Flow 解析或执行链，也不能通过直接请求 API 绕过页面入口门。
- route 只是把 URL 解析到 Flow 及其声明的机制，不是另一个配置或业务事实来源。
  修改、禁用或删除 Flow 及其声明后，入口行为必须与当前 Flow 状态一致。
- 页面 schema 只允许当前 namespace 或父级 namespace 的 `nsfile:///` 文件。
  不允许引用兄弟或无关 namespace，不允许通过路径穿越扩大解析范围。
- API 必须认证，不支持匿名。执行模式默认 `ASYNC`，`SYNC` 必须显式声明。
  不以 SSE 作为 API 契约。
- 页面访问、API 调用和执行结果必须关联到同一个承载 Flow，不能用一个 Flow
  的授权访问或触发另一个 Flow。

## 3. URL 与原生路由优先

统一应用 URL 前缀为：

```text
/{namespace}/{flow_id}/...
```

namespace 和 Flow ID 来自实际承载 Flow，不引入独立 appName 替代 Flow ID。
本需求不固定前缀之后的字段名称、页面/API 子路径或 Java 类型名称。

当 namespace 对应路径与 Kestra 内置 URL 冲突时，以上游 URL 为准。
扩展不得覆盖、抢占原生路由，也不得在原生路由返回错误时将它当作 AMIS 请求处理。
此规则同时适用于原生认证、API、UI、静态资源和健康检查路径。

URL 的编码和路径安全检查必须保留，不能通过编码或路径穿越绕过原生路由优先规则。

## 4. 统一权限配置

`kestra-plugin-amis-apps` 与 `kestra-plugin-rbac` 均是 Kestra UI 应用的扩展。
新增扩展仓不等于新增身份目录中的应用。

- 不因本功能新增 OAuth client、应用成员、应用组、scope 或管理 tab。
- 不在“概览、scope、应用组”等管理导航中增加“应用”入口。
- 使用既有 `kestra-ui` 应用的“应用运行时权限”维护入口能力明细，并关联已有 scope。
- 已有等价入口能力明细时直接复用，不重复追加；缺少时才增加一条。
- 不要求每个页面、API 或 schema 文件各登记一条权限。
- 入口能力的范围表达和前缀解析规则与既有 Flow 权限明细一致，不另造范围语法。
  例如 `company.*` 不匹配 `company2`；精确范围和补集语义保持一致。
- 权限明细名称或 key 本身不是授权结果。不得只因 URL 前缀匹配就放行业务。

入口能力只决定“是否允许按 AMIS 约定进入 URL 解析流程”。它不证明 namespace、
Flow 或声明路由存在，也不授予 Flow 执行权限。

## 5. 职责与请求顺序

### 5.1 职责

| 项目 | 职责 |
|---|---|
| `kestra-overlay` | 提供可被未来扩展复用的通用扩展入口能力门、原生路由优先、可信身份传递和评估调用机制；仅在现有公开机制不足时增加最小通用契约 |
| `kestra-plugin-rbac` | 统一权限维护、当前身份与 scope 的支持/授予及运行时策略评估、撤权，以及既有 Flow 执行授权 |
| `kestra-plugin-amis-apps` | 登记入口能力及范围规则，覆盖 PageTrigger 页面 URL 和 ApiTrigger API URL；在通用机制下判断是否进入自身解析；放行后解析 URL、查找 Flow 和声明、请求 Flow 执行授权，最后提供页面/API |
| `kestra-monorepo` | 选择正式产物、配置 Compose、协调发布顺序并执行真实组合验收，不实现 AMIS 业务 |

AMIS 插件通过公开机制消费 RBAC，不读取其私有表，不复制策略或另建许可名单。
overlay 不承载 AMIS schema、页面/API 声明或应用业务。

### 5.2 严格请求顺序

| 顺序 | 行为 | 负责项目 |
|---|---|---|
| 0 | 保留原生路由优先和生产认证；原生冲突请求不进入 AMIS | overlay |
| 1 | 对 PageTrigger 页面 URL 和 ApiTrigger API URL 统一判断当前可信身份及 scope 是否具有进入 AMIS URL 解析的入口能力；此时不查询 namespace、Flow、schema 或 Flow 执行权限 | overlay 提供通用门；RBAC 提供统一权限评估；AMIS 提供能力及范围 |
| 2 | 第一门允许后，按 namespace、Flow ID 解析并查找对应 Flow 和声明路由；不存在时正常返回 404 | AMIS Apps |
| 3 | 找到目标后，验证该具体 Flow 的执行权限；拒绝时停止 | AMIS 通过公开机制调用 RBAC 的既有 Flow 授权 |
| 4 | 两道门均允许后，读取声明 schema、提供页面或触发 API 执行 | AMIS Apps；实际执行使用现有宿主执行链 |
| 5 | 后续访问继续接受当前权限、撤权和适用的执行输出检查，不能沿用过期入口许可 | overlay、RBAC、AMIS 按各自职责共同完成 |

第一道门拒绝时不得查找目标，也不能通过不同响应透露 Flow 是否存在。
只拥有入口能力时，目标不存在返回 404；目标存在仍须通过 Flow 执行权限。
只拥有 Flow 执行权限时，不得绕过第一道入口能力门。

通过两道门后，读取当前或父级 namespace 的 schema 不再叠加额外文件级授权。
该规则不删除 RBAC 已有资源类型，不跳过现有执行链、输入/输出校验或执行结果权限。
页面访问许可也不授予修改 schema 或 Flow 的权限。

## 6. 安全与兼容

- 不支持匿名入口。浏览器使用生产登录流程；直接访问应用 URL 后，认证成功应返回
  原目标。cookie 写请求保留 CSRF，不能因使用简化 URL 而绕过。
- scope 授予、入口能力或 Flow 权限撤销后，后续请求必须遵守既有撤权与 refresh 机制。
  AMIS 不保存独立授权副本。
- 执行查询必须验证执行属于承载 Flow，不能通过任意执行 ID 访问其他 Flow 的结果。
- 必需组件缺失、授权依赖异常或资源计划无法确定时失败关闭。
- 拒绝请求不能创建 execution，不能写队列、存储或留下延迟业务副作用。
- 共同使用的 overlay 必须兼容模式 A 和模式 B。关闭 RBAC 时按宿主既有关闭语义
  工作，不伪造 scope，不要求授权插件存在；认证、URL 安全和原生路由优先保持有效。
- 新扩展停用或缺席时，不影响宿主原生路由和其他扩展。

## 7. 项目与文档边界

本文件处于需求阶段，描述目标行为，不将参考实现或当前基线的限制视为唯一技术
方案。一个 Flow 承载 AMIS 页面/API、JSON 驱动、当前 URL 策略、原生路由优先、
两道门顺序及项目分工是当前需求基线；具体类、SPI、路由排除方式、缓存、schema

若新增约束或当前机制限制会导致扩展架构级变化，实施 agent 必须先提交可核对的
失败证据、约束来源、最小替代方案、权限与兼容影响及测试计划。主控先判断能否
调整技术约束，不能为守住未经证实的手段而重做整体架构。可逆的实现细节由主控
自主裁决；涉及已确认总体目标、URL 策略、授权语义或项目边界的改变，必须向维护者
说明并取得裁决，再同步本需求与所属仓契约，不能静默改需求或先改后报。

外部评审、局部框架探针或旧项目限制是证据输入，不能直接升级为新增产品约束。
需求定稿不等于实现已确定，也不要求未知机制未经验证就写成现有能力。

### 7.2 单一文档归属

AMIS Apps 的业务声明、页面运行时、API 处理、schema 解析及自身测试归新扩展仓。
宿主只提供公共机制；根仓只维护组合与集成要求，不把业务代码放入根仓。

新扩展业务 README 与公开契约维护具体字段、类型和命令。本需求不固定参照的触发器

目录页和机器调用不能仅凭参照中存在而自动纳入某阶段。具体实现不得从参照代码
直接推导为当前唯一方案。

业务文档建立后，本文件保留跨仓目标、职责、顺序和组合验收要求，避免多处重复维护。

### 7.3 实施设计必须交代的边界

- **路由与 CSRF**：不能假定框架自动保证原生路由优先。宿主必须验证 Controller、
  静态资源、OAuth 及租户别名路径的实际顺序；使用保留首段、扩展注册或其他公共
  机制实现目标均可。简化 API URL 必须获得等效 CSRF 校验，SameSite 不能替代。
- **schema 与资源**：独立入口文档、schema 数据、运行时脚本/CSS/字体及编辑器资产
  必须分别定义装载路径、身份状态和所需授权。页面可达不能证明依赖资源可达。
  父级解析必须明确查找顺序与 JSON/schema 类型校验，不能把任意父级文件当页面
  返回；具体校验或目录约定由设计论证，不直接复制旧白名单或固定目录。
- **权限与读取**：公开列出页面、schema、POST、轮询和输出所需的完整既有操作计划，
  区分入口能力与执行链前置条件，不能将“Flow 执行权”简化成单一枚举检查。
  查找接口若需绕过存储 ACL，必须说明与两门顺序的关系及保护范围，不能借此读取
  schema 或暴露 Flow 内容。保留“入口允许后目标不存在404”的当前裁决；若响应差异
  形成不可接受的信息边界，按 §7.1 提出替代方案，不自行改成统一403或删除入口门。
- **Flow 内冲突**：URL 含 Flow ID，不继承旧全局 appName 查重。重点校验同一 Flow
  内重复页面/API 声明及跨类型路径冲突，并在保存/激活和请求时保持明确失败行为。
- **有界运行**：定义请求体、schema/资产、SYNC 等待及并发、轮询的上限、取消和
  资源释放规则，以边界值、超限与清理测试证明，不在需求阶段凭空固定数值。
- **受限用户**：没有宿主 dashboard 权限的账号也必须能从应用书签登录并回到目标，
  拒绝页可以退出换号；不要求增加目录页才能使用应用。
- **宿主接收**：涉及退役 Apps 域的公共机制时，遵守 overlay 重新接收规则，先登记
  差异表归属和消费方证据，再裁决最小提案；不能以本需求为由恢复旧业务 patch。
  JVM ServiceLoader 实验只证明类加载层，仍须验证宿主插件 schema 与 Flow 保存校验。

## 8. 验收要求

独立仓使用已发布公开契约和正式产物构建，不依赖相邻源码或未发布 jar。
宿主验证通用机制，RBAC 验证统一策略兼容，AMIS 验证自身业务及真实浏览器页面，
根仓验证正式组合；任何一仓通过不能替代其他仓职责。

| 验收项 | 必须证明的结果 |
|---|---|
| Flow 承载 | 同一 Flow 声明页面及其 API，变更后无需构建应用专属前端包；无独立应用/路由事实源 |
| 路由 | namespace/Flow URL 可达；不存在目标正常404；原生 URL 冲突始终由上游处理 |
| 首门拒绝 | PageTrigger 和 ApiTrigger 两类 URL 均拒绝；namespace、Flow、schema 查询和 Flow 执行授权调用均为零，无业务副作用 |
| 仅入口允许 | 不存在目标404；存在但无执行权限时拒绝，不读 schema、不创建执行 |
| 仅执行允许 | 不得绕过入口能力门 |
| 两门允许 | 真实登录后页面可用，表单/API 实际触发承载 Flow，核对执行与保存结果 |
| 权限配置 | 使用现有 `kestra-ui` 运行时权限及已有 scope；等价明细不重复追加，无新应用成员、scope 或管理 tab |
| Schema | 当前及父级 namespace 文件可用，无额外文件授权；兄弟/无关范围及穿越请求拒绝 |
| 执行模式 | 默认 ASYNC；显式 SYNC 有效；对外 API 不依赖 SSE |
| 撤权 | 分别收回入口能力、Flow 执行能力或 scope 授予，验证后续请求和 refresh 行为 |
| 拒绝副作用 | 检查 execution、队列、存储及延迟副作用，不以错误状态码单独证明拒绝正确 |
| 页面质量 | 按所属仓规则验证中文/英文、主题、窄屏、焦点、正常与错误状态；根仓不重复完整视觉矩阵 |
| 共存与关闭 | 模式A/B、与RBAC共存、新扩展停用/缺席均符合共同宿主与组合边界 |

## 9. 发布顺序

1. overlay 完成必要的公共机制，通过自身检查与 CI，发布正式镜像；无需变更的
   已发布能力只核实复用，不为形式完整制造新发布。
2. RBAC 按需要适配通用入口能力的统一维护与评估；AMIS 独立消费正式宿主契约，
   通过各自 CI 并发布正式产物。独立仓之间不读取相邻源码或触发对方构建。
3. 根仓选择兼容的正式镜像和插件，执行 Compose、真实生产登录与完整集成验收，
   核对最终提交成功 CI、实际下载报告、digest、jar hash、provenance 和资源清理。

## 10. AMIS 能力分阶段规划

以下阶段来自目标参照的文档与源码调查，不表示本轮已部署复验参照的全部能力。
调查入口为 `~/dsh-monorepo/docs/dsh-apps-amis.md`、`dsh-apps-amis-editor.md`，以及
参照仓 `ui/src/apps/main.ts`、`editor.tsx`、`AppRouterController` 和 `AppsFileController`。
参照中的 `PageTrigger`、`ApiTrigger`、
`AppRouteRegistry`、`apps.html`、AMIS runtime 和 `amis-editor` 是行为参考，不是当前
扩展必须复制的类名、包名、路由格式或内部实现。每阶段必须在前一阶段通过后再进入。

每阶段都遵守第 9 节发布顺序。新增宿主契约必须先完成宿主自身 CI 和正式发布，
再供独立扩展编译消费；扩展阶段产物可独立发布，根仓在该阶段执行必要组合验收。
P4 是完整能力集合的最终验收，不延迟 P0–P3 的依赖发布和必要组合门，也不把候选
开发输入或局部通过转为正式证据。前阶段只能宣称其明确范围已交付。

### P0：最小可运行闭环

目标是证明“一个 Flow 可以承载一个可打开的 AMIS 页面和一个受保护的 API”。

必须交付：

- Flow 声明页面入口和 API 入口；PageTrigger/ApiTrigger 可以作为参考命名，但不固定
  Java 类型名称。
- 第一层入口能力门同时覆盖页面 URL 和 API URL，并严格执行本需求第 5 节顺序。
- 页面 URL 使用 `/{namespace}/{flow_id}/...`，原生 Kestra URL 优先。
- 页面入口完成登录、schema 读取和 AMIS JSON 渲染。
- schema 使用当前或父级 namespace 的 `nsfile:///`；兄弟 namespace、路径穿越和非法
  schema 请求失败关闭。
- API 使用认证请求创建承载 Flow 的 execution；默认 ASYNC，返回稳定的 execution 标识
  和轮询信息；不使用 SSE。
- 页面和 API 均通过现有 Flow 执行授权，拒绝时不创建 execution、不写队列。
- 扩展不建立应用表、路由事实表或独立权限表。

P0 浏览器验收必须完成：

1. 首装、登录和直接访问页面。
2. 页面 DOM 中出现真实 AMIS 控件和页面数据，不以入口 HTML 或 HTTP 200 代替。
3. 页面 API 请求成功并保存真实 Flow execution。
4. 未登录、入口能力拒绝、Flow 不存在、Flow 执行权限拒绝分别验证。
5. 页面 URL 和 API URL 各覆盖存在与不存在目标，分别记录第一门拒绝时 namespace、
   Flow、schema 查询及 Flow 执行授权调用均为零的轨迹；第二门拒绝时 schema 读取
   为零且无副作用。独立探针不能替代真实生产身份和浏览器流程。
6. 浅色/深色主题、中文/英文、窄屏和键盘焦点。

### P1：真实页面交互与 API 场景

目标是证明 AMIS 页面不是“只能显示 JSON”，而是可以完成常见业务交互。

必须覆盖：

- 文本、数字、选择器、日期、开关、数组和必填校验。
- 表单提交、成功提示、失败提示和服务端错误。
- 条件显示、条件请求和页面级数据加载。
- 表格/列表查询、分页或加载状态，以及空数据状态。
- 对话框或抽屉中的表单提交。
- API ASYNC 轮询：初始执行、运行中、成功、失败、超时和暂停状态。
- 显式 SYNC 的成功、执行失败、等待到期和随后状态查询；未声明模式仍为 ASYNC。
  扩展公开契约必须定义等待上限、到期响应、执行是否继续及客户端恢复方式，不能
  把轮询超时当作同步等待到期；等待到期、刷新或重试不能隐式额外创建 execution。
- API 响应中的业务数据、错误消息和执行状态在 AMIS 页面中正确显示。
- 重复提交、刷新页面、离开页面和重新进入页面的行为。
- 拒绝 POST 的数据库、队列、execution 和延迟副作用为零。

P1 必须使用真实浏览器和真实 Flow execution。组件存在、mock API、Happy DOM 或
静态 JSON 不能代替交互验收。

### P2：同一 Flow 的多页面与多 API

目标是证明一个 Flow 可以承载完整 AMIS 应用，而不是只能承载单页示例。

必须覆盖：

- 同一 Flow 的首页、第二页面和页面间导航。
- 同一 Flow 声明多个 API，页面分别调用不同 API。
- API 路由身份不能由请求体伪造；路由解析结果必须优先于 body 中的同名字段。
- 页面 schema API 返回完整 AMIS schema 对象，并能被页面原生加载。
- 多个 API 分支互不串数据，响应不泄漏其他分支的输出。
- 公开契约定义 API、execution 与结果来源的绑定，不能仅证明 execution 属于同一
  Flow。用同 Flow 的 A/B API 不同结果验证交叉 execution ID、伪造 API ID、缺失/
  非法结果及输出持久化延迟；不得把缺失结果当空成功，继续遵守现有输出权限。
- 同名路径冲突、Flow 禁用、trigger 禁用、Flow 删除和 Flow 更新后的路由行为。
- 若使用派生缓存，验证更新失效和重启重建；若使用事件传播，验证其窗口，不强制
  复制参照的广播索引。扩展契约定义声明版本一致性、传播上限和超限失败行为。
  记录更新/禁用/删除时点、请求观察版本和停止使用旧声明的时点，不混用新旧声明。
  撤权独立遵守既有安全契约，缓存不得保留过期授权或无限延长传播窗口。
- 同一 Flow 在模式 A、模式 B 下的行为差异仅来自既定 RBAC 边界，不得有直接放行。

P2 必须保留每个 API、页面和 Flow 的明确来源证据，并验证跨 Flow 访问、错误 API ID、
错误 namespace 和已撤权账号均失败关闭。

### P3：AMIS 编辑器与页面资产生命周期

目标是实现参照项目中的编辑器能力，但使用当前扩展机制，不修改 Kestra 上游 UI 源码。

必须覆盖：

- 独立编辑器入口，不与宿主原生 UI 文档混用。
- namespace file 树和页面列表。
- 打开 JSON schema、AMIS 可视化编辑、预览、保存和刷新读回。
- 保存操作使用生产认证、CSRF 和现有 schema 写入边界。
- 编辑器和渲染页面的前端构建产物分离；渲染页面不加载编辑器大包。
- 明暗主题、中文/英文、窄屏、键盘焦点和错误状态。
- JSON 非法、schema 根类型错误、路径越界、并发覆盖和保存失败的明确处理。
- 编辑器不得因为页面访问权限自动获得修改 Flow 或 namespace file 的权限。
- 编辑器不提供任意外部 URL schema。进入 P3 前，扩展仓必须明确父级来源的只读/
  修改规则及所需管理权限；运行时允许读父级本身不授予编辑权限。保存目标必须
  显式绑定 namespace 和明确路径；不得静默覆盖父级文件或另存到当前 namespace。
  文件树、读取和写入分别遵守现有管理权限；运行入口免额外文件授权不延伸到编辑器。
  验证只读访问、无目标写权限时父级保存拒绝、路径替换、CSRF 缺失及失败前后文件
  字节不变；如接收授权父级写入，必须另有明确目标授权与保存读回的具名用例。

P3 的编辑器验收必须真实保存 namespace file，并刷新渲染页面验证保存结果；不能只
验证编辑器组件存在或本地状态改变。

### P4：生产集成与发布硬化

目标是完成与当前三仓、RBAC 和生产部署的正式组合。

必须覆盖：

- overlay 的通用入口能力门正式契约、原生路由优先和缺组件失败关闭。
- AMIS Apps 独立 jar 从已发布 overlay 镜像编译，不读取相邻源码或未发布 jar。
- RBAC 入口能力明细的复用/新增规则，scope 支持与授予交集及撤权 refresh。
- 既有等价权限明细不重复追加；管理页面不出现新的“应用” tab。
- Compose 模式 A、模式 B、扩展缺席、扩展关闭和错误配置回归。
- 真实登录、退出换号、直接 URL、刷新、拒绝写副作用和 execution 输出边界。
- 正式镜像 digest、插件 jar SHA-256、provenance、CI 报告和部署组合一致。
- README、公开契约、需求文档和实际命令一致。

P4 通过后，才允许把 `kestra-plugin-amis-apps` 加入根仓扩展清单的“已接入”状态。

### 阶段之间的停止条件

- P0 未通过，不开始 P1 的复杂控件和编辑器。
- P1 未通过，不开始 P2 的多页面、多 API 和复杂响应。
- P2 未通过，不开始 P3 的编辑器写入能力。
- P3 未通过，不宣布 P4 完整能力验收通过；各阶段必要的正式依赖发布和根仓组合
  验收按本节总则提前执行，不等待 P4。
- 任一阶段发现 overlay 公共机制不足，先按职责形成最小通用契约，再继续该阶段；
  完成自身 CI 与正式发布后再供扩展消费，不把 AMIS 业务特例写进 overlay。
